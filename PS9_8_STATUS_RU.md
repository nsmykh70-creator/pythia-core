# PYTHIA PS9.8 — шаг записи (lane transpose) и точный подбор рекуррентности

Основа: PS9.7. Формат контейнера не менялся (добавлен model ID 12, он описывается обычным дескриптором с одним байтом параметра).

## Что добавлено

1. **`LaneTranspose` (model ID 12).** Один байт параметра — шаг записи 2..=255. Выход: байты полей записи лежат подряд (колонка 0, колонка 1, ...). Сохраняет длину, обратим для любой длины входа, поэтому граница `max_transformed_block_len` не затрагивается.
2. **`detect_record_stride`.** Для лагов 2..=64 считается концентрация гистограммы разности `x[i] - x[i-лаг]` (целочисленная, фиксированная точка). Побеждает наименьший лаг, который не хуже лучшего более чем на 1/16 (кратные лаги проигрывают); лучший должен минимум вдвое превосходить лучшее из «сырые данные» и «лаг 1». Только эвристика писателя: декодеру она не нужна.
3. **Конвейер.** Если шаг найден, на полном блоке точно оцениваются цепочки `[Transpose(S)]` и `[Transpose(S), Delta8]`; выбор по точной сумме «дескриптор + кадр». Общая функция `evaluate_full_candidate` проверяет границы дескриптора и преобразованного потока.
4. **Подъём коэффициентов по битам** в `fit_algebraic_recurrence`. Остаток по модулю 2^k зависит только от коэффициентов по модулю 2^k, поэтому коэффициенты определяются по уровням k=1..8 (beam 16, выборка 1024 байта, детерминированная сортировка). Результат принимается только если он строго лучше по концентрации остатка на выборке 4096 байт, чем результат прежнего покоординатного спуска; на шумных данных прежний результат сохраняется.

## Измерения (Python, не Rust и не архив PYTHIA)

Калибровка детектора на первых 64 КиБ сегментов `mixed_10mb_compression_test.bin` (отношение лучшей концентрации к базе): records — шаг 16, отношение 5,16; text 0,39; skewed 0,50; markov 0,79; smooth 0,90; sparse 0,96; repeats 1,01; random 1,00. Порог 2 даёт срабатывание только на `records`.

Сегмент `records` (1 МиБ), размеры внешних компрессоров как грубый прокси контекстного кодера:

| Представление | zlib -9 | bzip2 -9 | xz |
|---|---:|---:|---:|
| исходные | 699 168 | 737 494 | 492 832 |
| transpose16 | 367 376 | 365 675 | 358 432 |
| transpose16 + delta | 368 454 | 360 269 | 360 848 |

Подбор рекуррентности (Python-зеркало алгоритма Rust): Fibonacci mod 256 — прежний `[110,0,95,212]` (7850 ненулевых остатков из 8192), новый `[1,1,0,0]`; рекуррентность `2·x₁+3·x₂` — прежний `[3,0,0,0]`, новый `[2,3,0,0]`; на сегментах text, markov, smooth, repeats, random подъём находил худшие по концентрации коэффициенты и не принимался (результат прежний).

## Что НЕ сделано и ограничения

- Не реализован фазовый контекст в энтропийном кодере. Транспозиция даёт кодеру подряд идущие поля, но таблицы частот не раздельные по колонкам. Прокси (энтропия порядка 0 для `records` после дельты с лагом 16): 4,33 бит/байт общая против 2,76 с раздельными таблицами по колонкам, то есть часть потенциала осталась.
- Не реализованы целочисленный LPC с фиксированной точкой и повторный подбор параметров по сегментам (обсуждалось отдельно; на `smooth_signal` оценка выигрыша мала, около 0,11 бит/байт).
- Стоимость: на блоках с найденным шагом добавляются две полные оценки `encode_best`; подъём коэффициентов добавляет порядка 10–20 мс на блок (оценка по числу операций, не замер).
- Rust-сборка и `cargo test` не выполнялись (в среде нет `rustc`/`cargo`).
